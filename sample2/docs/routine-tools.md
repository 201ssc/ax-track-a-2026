# 루틴 항목 도구 계약

기준: 2026-10-23. 개인 MVP의 첫 채팅 도구 범위는 루틴 항목 자체의 추가·삭제다. 날짜별 답변을 입력·지우는 기능은 이번 범위가 아니다. SQLite 공통 명령과 화면·HTTP·채팅의 제안/확인 연결을 구현했다. 설정된 Gemini가 루틴 추가·삭제를 해석하고 기존 일정·목차·조회는 각본 대역을 유지한다. 현재 명령의 필드·오류는 [명령 계약](command-contract.md)을 따른다.

항목 추가·삭제라는 범위와 기존 제품의 과거 보존 규칙은 확정 기준이다. 아래 공통 기능 분리·입출력·검증 통합은 이를 구체화한 설계 초안이며, 세부 기술을 사용자가 직접 지정했다고 해석하지 않는다. SQLite 저장 코어와 공통 명령은 구현으로 채택했다. 다음 구현의 저장·API·제안 영속화 기준안은 [저장·서버 설계](storage-server.md)에 있다. 구현 시 채택한 계약과 남은 미정을 갱신한다.

## 이전 구현과 현재 연결

| 기능 | 이전 브라우저 코드 | 현재 구현 |
| --- | --- | --- |
| 항목 추가 | 정해진 문장 → 목차 선택 → O/X 항목 제안 → 확인 후 localStorage 저장 | 서버에서 공통 추가 기능을 검증해 제안 보관, 사용자 확인 뒤 저장 |
| 항목 제거 | 답변이 있으면 중지, 없으면 삭제 | 답변 유무와 관계없이 공통 항목 삭제. 과거 답변·문항 사본·리포트 유지 |
| 저장 | 브라우저 전체 상태 저장 | Node.js 공통 변경 기능 → SQLite. 실제 DB 재조회·브라우저 검사 통과 |
| AI | 규칙 기반 문장 해석만 있음 | Gemini 실제 호출·구조화 출력·서버 검증·확인/저장 연결. 대역 검사와 실제 호출 검증 구분 |

현재 구현 근거: [respondChat/applyChatAction](../chat.mjs), [deleteQuestion](../model.mjs), [화면 조작·chatConfirm](../app.js). 관리 화면 삭제가 목표 삭제의 기준이다. 기존 ‘사용 중지’ 기능은 별도로 유지한다.

## 공통 처리 계약

기능은 ‘해석 → 대상 확인 → 제안 → 사용자 확인 → 검증·저장 → 화면 반영’으로 처리한다.

- 해석 결과 자체에는 저장 권한이 없다. 제안과 대상 선택 단계에서는 확정 데이터를 바꾸지 않는다.
- 같은 이름이 여러 개면 목차·항목 후보를 제시하고 사용자가 선택한 ID로 처리한다. 임의로 첫 항목을 선택하지 않는다.
- 확인 시 대상의 최신 상태를 다시 검사한다. 이미 삭제됐거나 제안 이후 변경됐다면 재요청 또는 새 제안으로 처리한다.
- 취소는 저장하지 않는다. 확인을 반복하거나 저장 응답이 끊겨 재시도해도 같은 변경이 중복 적용되지 않도록 한다.
- 화면 조작과 채팅은 동일한 추가·삭제 규칙을 호출한다. 저장·검증을 해석기마다 복제하지 않는다.
- 화면에는 실제 저장 성공 이후 성공을 표시한다. 실패 시 재시도할 내용을 유지한다.

## 추가 도구

| 항목 | 계약 |
| --- | --- |
| 필요한 값 | 대상 목차 ID, 항목 이름. 사용자가 말한 이름으로 목차 후보를 먼저 찾을 수 있음 |
| 기본 응답 형식 | 현재 채팅과 같은 O/X. 다른 형식의 자연어 생성은 첫 범위에 추가하지 않음 |
| 검사 | 목차 존재, 이름이 비어 있지 않음·80자 이내, 같은 목차의 삭제되지 않은 동명 항목 여부 |
| 제안 표시 | 목차 이름, 항목 이름, O/X 형식 |
| 확정 결과 | 새 ID의 활성 항목. 기존 답변을 생성하거나 과거 문항 사본을 변경하지 않음 |

동명 중복 거절은 현재 채팅의 동작이다. 관리 화면도 공통 추가 명령을 사용해 같은 검사를 적용한다. 기존 동명 자료를 자동 삭제·병합하지 않는다.

## 삭제 도구

| 항목 | 계약 |
| --- | --- |
| 필요한 값 | 삭제할 항목 ID, 제안 당시 상태를 확인할 정보 |
| 대상 | 현재 관리 목록의 항목. 이미 삭제된 항목 제외, 중지된 항목도 삭제 대상 가능 |
| 제안 표시 | 목차·항목 이름, 현재 목록에서 제거하며 과거 기록을 보존한다는 결과 |
| 확정 결과 | 현재 루틴·관리 목록에서 제거. 과거 문항 사본·답변·리포트 유지 |
| 후속 저장 | 같은 날 다른 답변을 저장해도 삭제 항목의 과거 기록을 잃거나 항목을 되살리지 않음 |

삭제와 중지를 자동으로 바꿔 실행하지 않는다. 채팅 테스트는 기록 있는 항목의 삭제·보존을 검사하며 관리 화면의 중지·재개 검증도 유지한다.

## 구현 경계와 수정 범위

- 요청 해석: `chat.mjs`의 정해진 문장 처리를 서버 `chat-service.mjs`에서 호출한다. 루틴 요청은 Gemini 어댑터를 호출하며 다른 기존 기능은 각본으로 처리한다.
- 공통 기능: 서버의 `commands.mjs`와 `model.mjs`. `applyChatAction()`은 이전 순수 함수 호환 검사에만 남아 있으며 화면·HTTP의 확정 변경 경로가 아니다.
- 저장: `app.js`의 비동기 `commit()` → `api.mjs` → HTTP 공통 명령 → SQLite. 실패 시 localStorage로 자동 전환하지 않는다.
- 표시: `app.js`의 제안·후보·확인·취소·결과 렌더링. 기존 `answer / proposal / choices`는 참고할 현재 형식이다.

첫 명령 이름은 `routine.create / routine.delete`, HTTP 경로와 확인 절차는 [저장·서버 설계](storage-server.md)의 기준안을 따른다. 필드별 JSON 스키마와 실제 파일 배치는 구현 시 구체화한다. 가계부의 ‘금액 유무로 기록/질문 분기’ 규칙은 사용하지 않는다.

기존 일정·리포트·목차 채팅 기능을 새 AI 도구로 한꺼번에 전환하는 것은 첫 범위에 포함하지 않는다. 기존 대역 기능은 유지하되 쓰기는 서버 전환 시 공통 저장 경로를 사용한다. 여러 사용자용 로그인, 대화 문맥 기억, 날짜별 답변의 AI 입력, 자동 조언은 별도 확장이다. 기존 화면의 날짜별 답변 입력은 계속 지원한다.

## 완료 확인 방법

아래는 현재 자동 검사가 확인하고 이후 확장에서도 유지할 완료 기준이다. 대역 자동 검사와 실제 모델 호출 검증은 구분한다. 소수 실호출 통과를 전체 품질 보장으로 해석하지 않는다.

- 추가·삭제 각각에서 제안 전/확인 전 데이터 불변, 취소 시 불변, 확인 후 저장을 확인한다.
- 동명 후보 선택, 없는 대상, 빈 이름·초과 길이·중복 이름, 오래된 제안, 중복 확인을 확인한다.
- 실제 저장 경로를 다시 읽어 결과를 확인한다. 서버 저장을 선택했다면 메모리 대역 통과만으로 완료 처리하지 않는다.
- 삭제 후 현재 목록 제외, 과거 문항·답변·리포트 유지, 당일 추가 저장 후 보존을 확인한다.
- 화면과 채팅에서 같은 기능의 결과를 대조하고 기존 중지·재개 동작도 확인한다.
- 저장 실패 시 성공 표시 없음, 재시도 시 중복 반영 없음, 입력 유지 여부를 확인한다.
- 실제 LLM 없이 테스트 대역으로 해석 결과부터 저장·화면 반영까지 확인한다. 대역 사용을 표시하고 ‘실제 AI 검증 완료’로 보고하지 않는다.

세부 실행 검사는 [검증 기준](verification.md)을 따른다. 저장 코어 검사 통과와 위 채팅 연결의 전체 완료를 구분한다.

현재 실행·API·제안 저장 계약은 [HTTP 계약](http-contract.md), 현재 검사 결과는 [HANDOFF.md](../HANDOFF.md)를 따른다.

실제 Gemini의 필드·오류·외부 전송 범위와 별도 호출 검증은 [Gemini 계약](gemini-contract.md)을 따른다.
