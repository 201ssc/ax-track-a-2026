# 개인 MVP의 저장·서버 설계

기준: 2026-10-23. 상태: **HTTP·화면·SQLite 저장·채팅 제안/확인 연결 완료, Gemini 루틴 해석 연결 완료**. 사용자가 진행을 요청한 개인용 저장·서버 구조 검토의 결과다. 제품 범위는 기존 합의를 따르며, 아래 기술과 API는 이번 분석의 권고안이다. 사용자가 세부 기술을 직접 지정했다거나 서버가 이미 동작한다고 해석하지 않는다.

## 선택과 이유

**기존 HTML/CSS/JavaScript UI + Node.js 단일 서버 + SQLite**로 시작하는 안을 권고한다. 브라우저와 서버가 기존 JavaScript 기록 규칙을 공유하고, 서버만 DB를 수정한다. Gemini를 서버 해석 어댑터에 연결했으며 자세한 현재 계약은 [Gemini 계약](gemini-contract.md)을 따른다.

| 항목 | 기준안 | 이유·한계 |
| --- | --- | --- |
| 화면 | 현재 정적 UI 유지 | React 전환이나 UI 재설계 없이 저장 경로를 교체 |
| 서버 | Node.js 24 계열, ES modules, 작은 `node:http` 서버 | 기존 `model.mjs`를 가져와 쓰고 `app.js`에 남은 변경 규칙을 공통 기능으로 이동. 처음부터 UI/API/agent 프로세스를 분리하지 않음 |
| DB | SQLite, 서버의 로컬 디스크 파일 | 별도 DB 서비스 없이 트랜잭션·재시작 후 저장 유지 가능. 서버를 여러 대로 늘리는 설계는 아님 |
| 연결부 | `node:sqlite`를 저장 모듈 하나에 한정 | 확인 환경은 Node v24.18.1. 해당 버전의 모듈은 Release candidate 단계이며 완전 안정 API로 설명하지 않음 |
| 저장 형태 | 다이어리 상태 JSON + 수정 번호, 제안·중복 요청은 별도 테이블 | 현재 날짜별 문항 사본과 계산 함수를 보존하기 쉬움. 기록이 커지면 날짜별 테이블 등으로 분리할 비용이 있음 |
| 실행 범위 | 본인 PC의 `127.0.0.1`, 한 서버·한 다이어리 | 로그인 없는 로컬 개발용. 휴대폰·외부 접속·공개 배포는 아직 포함하지 않음 |

Python/FastAPI도 가능하지만 현재 JavaScript 규칙을 Python으로 중복 구현하면 날짜·삭제 보존·집계의 불일치 지점이 늘어난다. PostgreSQL은 여러 서버·동시 사용자 요구가 구체화될 때 재검토한다. JSON 파일만 저장하는 방식은 중복 요청과 상태 변경을 함께 확정하는 처리를 직접 구현해야 하므로 이번 기준안에서는 선택하지 않는다.

공식 근거: [Node v24.18.1 SQLite](https://nodejs.org/download/release/v24.18.1/docs/api/sqlite.html)는 `DatabaseSync`가 동기식임을 명시한다. [SQLite 사용 기준](https://www.sqlite.org/whentouse.html)은 애플리케이션 로컬 저장에 적합하며 DB 파일당 쓰기는 한 번에 하나라고 설명한다. 개인용의 짧은 저장에는 사용할 수 있지만 큰 JSON 처리나 느린 질의가 서버 요청을 지연시킬 수 있으므로 저장 모듈 밖으로 동기 DB 호출을 퍼뜨리지 않는다.

## 화면·기능·저장의 경계

```text
기존 화면 ── 명시적인 변경 요청 ──────────┐
                                          ↓
채팅 → 해석 대역 → 대상 선택 → 제안 → 확인 → 서버 공통 변경 기능 → SQLite
                                          ↓
                              저장 결과 + 수정 번호 → 화면 갱신
```

- `model.mjs`의 문항 사본·부분 저장·삭제 보존·집계 함수를 출발점으로 삼는다. `app.js`의 직접 배열 변경과 `chat.mjs`의 항목 변경은 공통 명령 처리로 모은다.
- 브라우저는 표시와 입력 검사를 할 수 있지만, 서버가 최신 상태를 읽고 규칙을 다시 검사한 뒤 저장한다. 브라우저가 만든 전체 상태나 과거 문항 사본을 그대로 덮어쓰는 API는 만들지 않는다.
- 기존 `validateState()`는 현재 저장 자료의 기본 형식 확인이다. 서버 입력 검증 전체를 대신하지 않는다. 요청 종류·허용 필드·ID·응답 형식·날짜를 명령별로 검사한다.
- 숫자는 기존 공통 계산 함수로 구한다. 초기 화면 집계는 서버에서 받은 상태로 브라우저가 계산해도 되며, 이후 AI에 제공하는 숫자는 서버에서 같은 함수로 계산한다.
- 시간대는 첫 개인 버전에서 `Asia/Seoul`을 기준으로 한다. 서버가 `today`와 시간대를 제공하고 날짜 판단에 공통 시계를 사용하도록 정리한다. 브라우저·서버 OS의 시간대 차이로 오늘/미래 판단이 달라지지 않아야 한다.
- DB 트랜잭션 안에서 AI나 다른 네트워크 응답을 기다리지 않는다. 해석은 먼저 끝내고 확정 저장은 짧게 처리한다.

## 저장 계약

현재 HTTP 서버 스키마 버전 2는 diaries·command_receipts·proposals를 사용한다. 실제 명령 필드·오류·실행법은 [명령 계약](command-contract.md)에 있다. v1에서 백업 후 proposals를 추가하는 마이그레이션을 구현했으며 아래는 책임 구분이다.

| 자료 | 최소 필드와 역할 |
| --- | --- |
| `diaries` | `id`, `revision`, `state_json`, `updated_at`. 첫 버전은 서버가 선택한 `personal` 한 건. 현재 `version:1`, `groups`, `questions`, `days`, 제목·일정·호환 자료를 포함 |
| `proposals` | 제안 ID, 다이어리 ID, 해석 후 검증된 명령, 기준 revision, 표시할 대상 정보, 상태, 생성/만료 시각, 적용 결과. 대화 전체 기억 기능과 구분 |
| `command_receipts` | 다이어리 ID + 요청 ID의 유일성, 정규화한 요청 해시, 성공 결과와 적용 revision. 응답 유실 뒤 재시도할 때 중복 반영 방지 |

DB 스키마 버전과 상태 객체의 `version`은 따로 관리한다. 마이그레이션 실패·손상·알 수 없는 버전은 저장 중단 사유이며 예시로 자동 초기화할 이유가 아니다. 다이어리 ID는 향후 저장 경계를 위한 값일 뿐 사용자 인증·격리가 구현됐다는 뜻은 아니다.

### 변경 하나의 처리

1. 요청 형식을 검사한 뒤 트랜잭션을 시작한다.
2. 같은 요청 ID의 성공 결과가 있으면 본문 해시를 비교한다. 같은 요청이면 기존 결과를 반환하고 다른 내용이면 충돌로 거절한다. **재시도 확인은 revision 검사보다 먼저** 수행한다.
3. 최신 상태의 revision과 요청의 `expectedRevision`을 비교한다. 다르면 저장하지 않고 `409 revision_conflict`를 반환한다.
4. 서버 상태를 기준으로 대상·입력·기록 규칙을 검증하고 새 상태를 만든다. 답변의 문항 구성도 서버에서 결정한다.
5. 상태, 증가한 revision, 요청 성공 기록을 같은 트랜잭션에서 저장한다. 채팅 확인이면 제안의 적용 상태도 함께 확정한다.
6. 커밋 후 성공을 반환한다. 실패하면 모두 되돌리고 화면 입력은 유지한다.

전체 다이어리 revision을 쓰므로 다른 탭의 무관한 수정도 충돌할 수 있다. 개인 MVP에서는 자동 병합보다 오래된 덮어쓰기 방지를 우선한다. 충돌 시 입력을 보존한 채 최신 자료를 다시 읽고 다시 확인하게 한다. 요청 ID는 사용자 조작 한 번에 발급하고 응답 유실 재전송에서는 재사용한다. 내용을 고친 새 요청은 새 ID를 쓴다. 첫 버전에서는 성공 기록을 자동 만료시키지 않으며, 정리 정책은 중복 방지 보장 기간과 함께 나중에 정한다.

### 예시와 파일 관리

- 새 DB를 명시적으로 준비할 때 기존 `createDemoState()`로 예시를 한 번 넣는다. DB가 이미 있으면 재시작·새로고침·날짜 변경으로 예시를 다시 생성하거나 섞지 않는다.
- 사용자의 기존 테스트 입력은 이전하지 않아도 된다. 서버 버전은 새 DB의 예시로 시작하며, 기존 localStorage를 자동으로 가져오거나 지우지 않는다. 이후 DB에 입력한 자료는 계속 보존한다.
- DB 경로는 설정 가능하게 하고 기본값은 OS 사용자 데이터 디렉터리(예: Linux `~/.local/share/iruo-habit-diary/diary.sqlite`)에 둔다. 정적 웹 제공 경로·Git·다른 앱의 자료와 분리한다. 이번 구현 검사는 임시 DB 경로만 사용했으며 기본 사용자 경로에 DB를 만들지 않았다.
- 테스트는 임시 DB 경로를 사용한다. 실제 초기화나 마이그레이션 작업에서는 대상 경로를 명시하고 백업을 먼저 만든다. 백업은 SQLite 백업 API 또는 정상 종료 후 복사로 만들고 별도 경로에서 복원 확인한다.

## HTTP와 채팅 연결 계약

아래 경로는 현재 구현했으며 상세 입력·상태·오류는 [HTTP 계약](http-contract.md)을 따른다. 정적 화면과 API를 같은 서버에서 제공한다. 새 서버의 기본 포트는 기존 정적 서버 8765와 겹치지 않는 8787로 사용하며 설정 가능하다.

| 경로 | 입력·결과의 책임 |
| --- | --- |
| `GET /api/diary` | `{state, revision, today, timeZone}`. 조회로 기록을 변경하지 않음 |
| `POST /api/commands` | 화면의 `{requestId, expectedRevision, type, payload}`. 허용한 명령만 처리하고 성공 시 적용 revision과 결과를 반환 |
| `POST /api/chat` | 문장 또는 후보 선택 ID → `answer / choices / proposal`. 첫 루틴 도구는 `routine.create`, `routine.delete`만. 문장·모델 출력만으로 확정 저장하지 않음 |
| `POST /api/proposals/:id/confirm` | 서버에 보관한 제안을 확인. 명령 본문을 브라우저에서 다시 받지 않음 |
| `POST /api/proposals/:id/cancel` | 대기 중인 제안을 취소. 다이어리 상태는 불변 |
| `GET /api/proposals/:id` | 응답 유실 후 적용/취소/대기 상태 확인. 대화 이력 조회 기능이 아님 |

확인·취소가 경쟁하면 먼저 확정된 결과가 유지된다. 적용 완료된 제안을 취소해도 기록을 되돌리지 않는다. 확인 재전송은 이미 적용한 결과를 돌려준다. 첫 구현의 제안은 24시간 만료를 기준안으로 삼되, 그 전에도 revision이 바뀌면 다시 제안·확인해야 한다. 제안 생성·취소만으로 다이어리 revision을 증가시키지 않는다. 제안 결과의 영속 보관과 화면 대화의 영속 보관은 다르며, 현재처럼 새로고침 후 대화 화면을 복원하는 기능은 필수가 아니다.

서버는 루틴 후보를 최신 자료에서 찾고, 같은 이름이면 사용자의 ID 선택을 받는다. LLM 어댑터는 추후 `{intent, arguments}`를 내는 해석기 역할만 맡는다. 확인/취소 엔드포인트와 저장 함수는 모델의 호출 가능 도구로 노출하지 않는다. 첫 테스트는 정해진 해석 결과를 주는 대역을 사용하고 실제 AI 연결로 표시하지 않는다.

로컬 서버는 허용한 UI 파일만 제공한다. DB·백업·환경 파일·저장소 전체를 웹에 제공하지 않는다. 쓰기 요청은 JSON과 같은 출처 검사, 허용 Host 검사로 제한한다. 이 조치는 다중 사용자 인증을 대신하지 않는다. 외부 접속을 추가할 때 별도로 인증·배포 범위를 설계한다.

## 기존 기능을 유지하는 전환 범위

**AI 도구 두 개와 기존 UI의 저장 기능은 범위가 다르다.** 첫 AI 도구는 루틴 추가·삭제지만, 서버 버전에서 기존 화면의 모든 쓰기는 같은 DB를 사용해야 한다.

| 현재 기능 | 서버로 옮길 공통 변경의 종류 |
| --- | --- |
| 루틴 관리 | 생성·수정·중지/재개·순서 변경·삭제. 관리 화면의 기존 응답 형식 네 가지는 유지하며 첫 채팅 생성만 O/X로 제한 |
| 목차 관리 | 생성·수정·순서 변경·빈 목차 삭제 |
| 날짜별 기록 | 부분 답변 저장·선택 답변 지우기. 서버의 날짜별 문항 사본과 삭제 기록 보존 사용 |
| 제목 | 내용 저장/지우기와 체크 상태 지정. 전날 답변과 함께 원자적으로 저장 |
| 일정 | 생성·수정·삭제와 체크 상태 지정. 날짜 이동의 체크 초기화 유지 |

현재 `toggle` 조작은 서버 요청에서 원하는 최종 상태를 명시하도록 바꾼다. 재시도 때 반대로 뒤집히지 않도록 요청 ID와 함께 처리한다. 리포트·날짜 이동·화면 탭 이동은 조회이며 저장 명령을 만들지 않는다.

기존 일정·목차의 각본 채팅도 UI 전환 때 같은 공통 저장 명령으로 연결하되, 새로운 AI 도구로 등록하지 않는다. 기존 목차 채팅의 일괄 중지처럼 관리 화면과 의미가 다른 각본 동작은 명시적인 호환 명령으로 유지한다. 이를 일반 목차 삭제에 섞지 않는다. 새 루틴 삭제만 [루틴 도구 계약](routine-tools.md)에 따라 항목 삭제로 변경한다.

서버 버전은 localStorage에 동시에 쓰지 않으며 서버 오류 때 자동으로 로컬 저장으로 전환하지 않는다. 그러면 성공한 것처럼 보이는 별도 기록이 생길 수 있다. 저장 대기·실패·충돌에서 입력을 유지하고 재시도를 제공한다. 현재 실행 경로는 HTTP 서버 하나이며 Python 정적 실행 경로와 localStorage 대체 저장은 제공하지 않는다.

| 저장 코어·공통 변경 기능 | `model.mjs`, 새 공통 명령 모듈, `server/`의 저장·서비스 모듈, 서버 테스트와 실행 설정 | 실제 임시 파일 DB의 프로세스 재시작 후 조회, 명령 실패 전체 롤백, 중복 재시도 1회 반영, revision 충돌, 삭제 후 과거 보존 |
| 기존 UI의 서버 전환 | `app.js`, 새 HTTP 연결부와 서버 경로, `boot.js`·캐시 갱신, 해당 브라우저 검사 | 모든 기존 쓰기가 DB에 반영되고 재접속 후 유지. 입력 유지·중복 클릭·통신 오류·다른 탭 충돌. localStorage 검사만으로 통과 처리하지 않음 |
| 첫 채팅 도구 연결 | `chat.mjs`, 서버 해석 대역·제안/확인 처리, 채팅 검사 | 확인 전 다이어리 불변, 선택·취소·확인·만료·재시도, UI와 같은 추가/삭제 결과, 실제 LLM 없이 전체 경로 확인 |

저장 코어의 실제 파일·명령은 [명령 계약](command-contract.md)에 반영했다. HTTP·화면 연결도 구현했으며 해당 계약에 반영했다. 존재하지 않는 서버 실행 명령을 README에 사용 가능한 것으로 추가하지 않는다. 구체 검사는 [검증 기준](verification.md), 보존할 동작은 [제품 규칙](product-rules.md), 가계부와의 차이는 [참고 분석](reference-account-book.md)을 따른다.

## 설계 검토 당시의 확인과 미검증 범위 (구현 전 기록)

- 확인: 설치 Node v24.18.1에서 `node:sqlite` 사용 가능, 내장 SQLite 3.53.1. 임시 메모리 DB의 생성·트랜잭션 저장 확인.
- 확인: 기존 `demo.mjs`와 `model.mjs`를 Node에서 가져와 예시 생성 → 기록 있는 항목 삭제 → 임시 파일 DB 저장 → 별도 Node 프로세스 재조회 후 상태 일치. 날짜별 답변과 리포트가 유지됨을 확인하고 임시 파일 삭제.
- 미검증: 실제 앱 HTTP API, 화면 연결, 서버 입력 검증, 중복 요청·충돌 처리, 백업 복원, 성능, 실제 LLM. 위 작은 실험은 이 기능들이 구현됐다는 뜻이 아니다.
- 남은 구현 세부: 명령별 필드 스키마, 실제 파일 배치, 패키지/실행 명령, UI의 비동기 처리. 해당 작업에서 코드·테스트와 함께 구체화한다.
- 후속 범위: AI 제공자·모델, 대화 기억, 외부/휴대폰 접속, 여러 사용자용 인증·권한, 대량 기록의 테이블 분리. 첫 저장 코어를 시작하기 위해 모두 먼저 정할 필요는 없다.

## 저장 코어 구현 결과

Node.js/SQLite를 첫 구현 기술로 채택했다. 공통 명령은 기존 모델 함수를 호출하고 서버 기준 날짜를 전달한다. 기존 브라우저 호출의 기본 날짜 동작은 유지했다. CLI로 명시적 초기화·조회·변경·백업이 가능하다. 화면·HTTP·확인 제안도 연결했다. 루틴 요청에는 실제 Gemini를 호출한다. 현재 검사 결과와 다음 작업은 [HANDOFF.md](../HANDOFF.md)를 따른다. 위 설계 검토 시점의 작은 실험·저장 코어 검사·현재 HTTP/브라우저 검사를 구분한다.
