- O = 실천 후 기록 완료, X = 미실천으로 기록 완료, 미선택 = 미기록. O/X 모두 제출하면 남은 항목에서 사라진다.

- 응답은 O/X, 단일 선택, 글쓰기, 점수. 문항별 한 가지 형식으로 시작한다.
- 오늘 날짜가 기본이며 날짜를 바꿔 과거 기록을 입력한다. 미래 기록은 받지 않는다.

- 목차·항목·보기의 추가/수정/순서 변경/사용 중지를 지원한다. 기록이 있는 항목은 사용 중지해도 과거 답변을 보존한다.
- 기본 리포트는 실제 저장된 기록만 집계한다. O/X의 실천 수와 응답 완료 수를 구분하고 미기록 날짜를 0점으로 계산하지 않는다.

- 저장 키 `habit-diary-sample2:v1`. 기록은 브라우저 localStorage에 저장하며 서버·다른 기기와 동기화하지 않는다.
- 제출 시 문항·목차·선택지의 사본을 날짜별로 보관한다. 과거 저장일의 문항은 당시 구성을 유지한다. 오늘의 항목 관리 변경은 현재 목록에 반영하며 이미 저장된 답변은 유지한다.
- 기본 점수 범위 1~5. 리포트 범위 최근 7일/30일, 선택 날짜가 기간의 마지막 날.
- 채팅·실제 AI·계정·푸시 알림은 이후 논의 대상이다.
- 기존 IRUO 및 sample 원본을 수정하지 않는다. 커밋·푸시·외부 배포는 하지 않는다.

- 홈에서 특정 항목을 직접 누르는 개별 확인·수정은 유지한다. 저장 버튼은 하나이며 작성한 응답만 저장한다.

## 오늘의 나에게 / 내일의 나에게

- 홈의 큰 진행 카드를 ‘오늘의 나에게’로 바꾼다. 전날 작성한 일정·할 일·다짐을 한 줄씩 표시한다. 체크는 선택이며 루틴 기록 수나 점수에 합산하지 않는다.
- ‘내일의 나에게’에 한 줄씩 입력하면 작성일 다음 날짜의 홈에 보인다. 날짜를 바꿔도 정확히 전날의 문장을 읽으며 미체크 문장을 자동 이월하지 않는다.
- 진행 현황과 전체 기록 버튼은 카드 아래 작은 영역에 둔다.

## 제목과 날짜 있는 일정 분리 · 최신 합의

- ‘내일의 나에게’를 ‘내일의 제목’ 한 줄로 바꾼다. 다음 날 홈에 표시하며 체크할 수 있다.
- 일정은 업무·공부에서 날짜와 내용을 지정한다. 미래 날짜도 등록할 수 있고, 지정된 날 홈에서 체크할 수 있다.
- 홈 상단에 ‘오늘의 제목/오늘의 일정’ 표제나 설명을 붙이지 않는다. 제목은 금색 계열, 일정은 옅은 녹색 계열로 구분한다. 체크박스는 둘 다 유지한다. 루틴 진행 영역은 작게 유지한다.
- `dayTitles`(표시 날짜별 제목)와 `schedules`(날짜가 있는 일정)를 기존 저장 키 안에 추가한다. 기존 `messages`와 날짜별 응답은 보존한다. 과거 문장을 임의로 제목/일정으로 해석하지 않고 제목 편집창에서 이전 문장을 열람하게 한다.

## 일정 추가와 달력 조회 분리 · 최신 합의

- 업무·공부에서는 ‘일정 추가’ 버튼만 표시한다. 등록된 일정 목록은 루틴 목차 안에 누적 표시하지 않는다.
- 기존 날짜 선택 영역 옆에 기록/달력 토글을 둔다. 달력에는 날짜별 일정 표시점과 선택 날짜의 목록을 보여주고, 등록·수정·삭제할 수 있다. 미래 날짜도 조회한다.
- 기록 화면으로 돌아오면 홈 상단에는 해당 날짜의 일정만 보인다. 달력에서 미래 날짜를 보고 돌아오면 기존 기록 날짜를 유지한다.

- 홈·달력·기록창뿐 아니라 채팅·리포트·항목 관리에도 같은 규칙을 적용한다. 최대 430px 휴대폰 기본 배치는 유지한다.
- 실제 shadcn 컴포넌트 설치나 프레임워크 전환 없이 기존 정적 앱의 CSS와 표시용 아이콘을 수정한다. 저장 모델·키·원본 데이터·채팅 확인 과정·미래 날짜 규칙은 변경하지 않는다.
- 참고 근거와 앱에 맞춰 정한 값은 `DESIGN.md`에 분리해서 기록한다.

## 휴대폰 하단 네비게이션 (2026-10-23)

- 오늘의 기록·기록 리포트·채팅·항목 관리를 상단에서 하단 고정 탭으로 이동한다. 브랜드는 상단에 유지한다.
- PC에서도 휴대폰 기본 배치를 사용하므로 하단 탭의 폭을 앱의 최대 430px에 맞춘다. 현재 메뉴의 강조와 접근성 상태를 유지한다.
- 본문 아래에 탭 높이만큼 여백을 두고 기기 하단 안전 영역을 반영한다. 저장 알림은 탭 위에 표시한다. 대화상자는 기존대로 탭보다 위에 열린다.

## 항목 관리의 밀도와 삭제 (2026-10-23)

- 버튼이 다음 줄로 넘어가던 배치를 없애고 이름·응답 방식·⋯ 메뉴를 한 줄에 둔다. 기본 행 높이는 51px로 한다. 장문의 상단 안내와 반복 조작 버튼은 제거한다.
- 이름을 누르면 바로 수정한다. 항목과 목차의 수정·이동·중지·삭제는 각각의 ⋯ 메뉴에서 실행한다. 메뉴는 바깥 클릭과 Escape로 닫히고 아래 공간이 부족하면 위로 펼친다.
- 삭제는 기록 유무와 관계없이 메뉴에 표시한다. 확인 후 현재 루틴과 관리 목록에서 제거하되 날짜별 문항 사본과 답변은 유지한다. 기록이 있는 항목에는 삭제 표식을 남겨 오늘 답변 사본에서 재등장하지 않게 한다. 이후 당일 다른 항목을 저장해도 삭제한 항목의 기록은 보존한다.
- 사용 중지는 삭제와 구분한다. 관리 목록에 남아 다시 사용할 수 있으며, 채팅의 기존 ‘빼줘’ 동작은 사용 중지로 유지한다. 삭제한 항목은 채팅 대상과 새 항목의 이름 중복 검사에서 제외한다.
- 이번 변경도 기존 정적 앱의 구현이다. 실제 shadcn/ui 컴포넌트를 설치했다고 표시하지 않는다.

## 개인 MVP와 첫 채팅 도구 범위 (2026-10-23)

- 사용자는 개인용으로 간단히 시작하고 고도화한 뒤 여러 사용자용으로 확장하기로 했다. 현재 범위에 여러 사용자용 가입·권한 전체를 포함하지 않는다.
- 가계부는 다른 사람이 만든 참고자료이며, 다이어리는 사용자가 만든 별도 구조다. 가계부 기술에 억지로 맞추지 않는다. 새 세션에서도 잘못된 수정을 줄이는 규칙·계약·검증 관리 방식을 주요 참고 대상으로 삼는다.
- 첫 채팅 도구 범위는 루틴 항목 자체의 추가·삭제다. 날짜별 O/X 답변 입력·제거를 뜻하지 않는다. 향후 확장하되 도구 전부를 한 번에 만들 필요는 없다.
- 새 채팅 삭제 목표는 관리 화면과 같은 항목 삭제이며 과거 문항·답변·리포트를 보존한다. 이 목표가 앞선 채팅의 ‘기록 있으면 사용 중지’ 규칙을 대체한다. 현재 코드는 아직 이전 동작이다.
- 사용자가 지금까지 넣은 자료는 테스트 입력으로 제거 가능하며 기본 예시는 유지한다. 앞선 개인 입력 보존 요구의 이 범위를 완화한다. 이후 입력을 매번 초기화하거나 항목 삭제 시 과거 답변을 지우라는 뜻은 아니다. 실제 초기화는 아직 하지 않았다.
- 최종적으로 AI를 연결해 MVP 작동을 확인하려 한다. 이번 구현 목표는 실제 AI 연결 전까지 준비하는 범위다. 현재 서버·저장 기술·AI 제공자·배포 방식은 미정이다.

## 작업 순서표 대신 문서 인덱스와 규칙 연결 (2026-10-23)

- 사용자는 고정된 작업 순서 문서보다 인덱스와 관련 규칙 문서로 작업 종류별 기준을 찾아가는 방식을 선택했다.
- `AGENTS.md`에서 `INDEX.md`로 안내하고, 인덱스가 제품 규칙·도구 계약·개발 규칙·검증 기준·참고 분석을 연결한다. 각 작업에서 수정 범위와 완료 확인 방법을 찾을 수 있도록 한다.
- 현재 규칙은 담당 문서에, 변경 이력은 이 문서에, 진행 상태는 `HANDOFF.md`에 둔다. 현재 구현과 미구현 목표를 구분한다.
- 문서 체계 작성은 서버·도구 구현 착수를 뜻하지 않는다. 앞선 FastAPI/PostgreSQL 선택 및 일정부터 구현하는 순서 제안도 확정되지 않았다.

## 개인용 저장·서버 구조 검토 (2026-10-23)

- 사용자가 다음 단계 진행을 요청하여 개인용 저장·서버 구조를 검토했다. 결과는 [저장·서버 설계](docs/storage-server.md)에 정리했다. 아래는 구현을 위한 기술 기준안이며 사용자가 각 기술을 직접 지정하거나 서버가 이미 구현됐다는 기록이 아니다.
- 기존 UI + Node.js 단일 서버 + SQLite를 권고한다. 현재 JavaScript의 날짜별 문항·삭제 보존·집계 규칙을 공유해 Python으로 다시 구현하는 비용을 줄인다. 가계부의 공통 처리·확인·중복 실행 방지는 참고하되 FastAPI/PostgreSQL이나 여러 서비스 분리를 강제하지 않는다.
- 첫 저장은 현재 다이어리 상태 JSON과 revision을 사용하고, 제안·중복 요청 결과를 별도로 보관한다. 화면이 전체 상태를 덮어쓰게 하지 않고 서버가 명령별로 최신 상태를 검증·수정한다. 상태·요청 결과·제안 적용은 한 트랜잭션으로 확정한다.
- 첫 AI 도구는 루틴 항목 추가·삭제다. 기존 화면의 답변·목차·일정·제목 저장도 같은 DB로 옮기는 작업이 필요하지만 이를 모두 새로운 AI 도구로 만든다는 뜻은 아니다. 서버 실패 시 localStorage로 자동 저장하는 이중 경로는 두지 않는다.
- 새 DB는 기존 예시로 한 번 준비하고 기존 localStorage는 자동 이전·삭제하지 않는 안이다. 개인 테스트 입력의 완전 이전은 필요 없다는 최신 합의를 적용한다. DB 재시작·새로고침으로 새 기록을 초기화하지 않는다.
- 첫 실행은 본인 PC의 로컬 서버다. 외부 배포·모바일 접속·AI 제공자·다중 사용자 인증은 후속 범위다. 개인 버전이 완성되더라도 다중 사용자 전환이 DB 교체만으로 끝난다고 설명하지 않는다.
- 별도 작업 순서표 대신 INDEX에 현재 작업과 다음 구현 대상을 표시한다. 이번에는 기준안과 임시 DB 실험만 완료했으며 제품 실행 코드는 변경하지 않았다.

## SQLite 저장 코어와 공통 명령 구현 (2026-10-23)

- 사용자의 구현 진행 요청에 따라 Node.js 24와 SQLite를 저장 코어에 채택했다. 상태·수정 번호·요청 성공 결과를 트랜잭션으로 저장하고 같은 요청 재전송을 중복 반영하지 않는다. 전체 상태를 받는 쓰기 기능은 제공하지 않는다.
- 루틴 관리뿐 아니라 후속 UI 전환에 필요한 목차·답변·제목·일정의 공통 명령과 필드 검증을 구현했다. 현재 화면과 채팅이 이 명령을 이미 호출하는 것은 아니다. 구체 계약은 [명령 계약](docs/command-contract.md)을 따른다.
- DB 스키마 버전 1은 diaries와 command_receipts다. proposals는 확인 흐름 연결 때 추가한다. 첫 단계에는 CLI 초기화·조회·변경·백업을 제공하며 HTTP·공개 접속은 아직 구현하지 않았다.
- 서울 기준 날짜를 모델 함수에 선택적으로 전달하고 기존 호출의 기본값은 유지했다. 새 DB 초기화는 기존 예시 생성 함수를 사용하며 이미 준비된 DB는 재초기화하지 않는다. 테스트는 실제 사용자 자료와 분리된 임시 경로만 사용했다.
- 단계 완료는 저장 코어·명령 검사 통과를 뜻한다. 기존 화면의 localStorage 저장과 각본 채팅은 다음 HTTP/UI 전환까지 남아 있다. 실제 AI 연동 완료로 표시하지 않는다.

## HTTP·화면·제안 확인 연결 (2026-10-23)

- 사용자의 나머지 작업 진행 요청에 따라 기존 UI의 모든 변경을 Node HTTP API와 SQLite 공통 명령에 연결했다. 화면은 더 이상 localStorage를 읽거나 쓰지 않는다. 기존 브라우저 자료는 자동 이전·삭제하지 않는다. Python 정적 서버 대신 `npm --prefix sample2 start`로 연다.
- 첫 루틴 채팅 도구의 추가·삭제를 서버 제안 → 사용자 확인 → 공통 명령으로 연결했다. 기록 있는 항목도 삭제하며 과거 문항·답변·집계는 보존한다. 이 동작이 기존 ‘기록 있으면 중지’를 대체한다. 관리 화면의 중지·재개는 유지한다.
- 기존 목차·일정·조회 각본은 유지하며 목차의 일괄 중지는 group.pause 호환 명령으로 구분한다. 실제 AI 도구를 전부 만든 것으로 설명하지 않는다. 해석은 여전히 규칙 기반이며 AI 제공자/키는 미연결이다.
- 스키마 v1 백업 후 v2에 proposals를 추가했다. 확인 반복·응답 유실·서버 재시작에도 제안 결과와 요청 결과로 중복 적용을 막는다. stale revision은 다시 제안하며 만료는 24시간이다.
- 통신 실패·수정 충돌에서 입력을 유지하고 재확인한다. 응답이 불확실하면 같은 요청부터 확인하며 자동 로컬 저장은 없다. 대화와 전송 대기 초안의 새로고침 후 복원은 아직 없다.
- .env.example은 선택적 로컬 설정 예시다. 실제 .env는 Git 제외이며 서버/CLI에서만 읽는다. 실제 API 키는 AI 연결 시에만 필요하다. 외부 접속·로그인은 범위에 포함하지 않는다.
- 자동 검사와 직접 사용감 확인을 구분하고 [직접 테스트](docs/manual-check.md)에 사용자가 확인할 범위를 연결했다.

## 환경 설정 예시 보완

- 가계부 .env.sample과 agent Settings의 제공자별 키·AGENT_MODEL 구성과 시크릿 분리 방식을 대조했다. 다이어리 .env.example에 다음 AI 연결용 키·모델·시간 제한을 추가하고 현재 읽는 포트·SQLite 경로와 구분했다.
- 키 하나와 그 제공자의 모델을 맞추는 방식을 참고한다. LiteLLM·특정 기본 모델·가계부의 PostgreSQL/RAG/MCP 설정을 자동 채택하는 것은 아니다. 아직 AI 설정을 읽어 호출·검증하는 어댑터는 구현하지 않았다.
- 없던 실제 .env를 빈 키의 예시로 준비했다. 실제 값은 .env에만 넣으며 기존 파일은 덮어쓰지 않는다. 사용자 직접 UI 확인은 이상 없음으로 기록했다.

- 실제 .env의 키·모델 값은 건드리지 않았다. 현재 단계는 예시와 방향 정리이며 AI 호출 코드는 아직 없다.

## Gemini 요청 해석과 실제 호출 검증

- 사용자가 .env 값을 넣었다고 알려 실제 연결을 진행했다. Node fetch의 Gemini 구조화 출력으로 루틴 추가·삭제 intent와 이름만 추출한다. AI가 대상 ID를 선택하거나 확인/저장을 실행하지 않는다.
- 루틴/목차 이름과 이번 요청만 전송한다. 답변·회고·점수·일정·전체 상태·대화 이력은 보내지 않는다. 모델 실패를 각본 쓰기로 자동 전환하지 않으며 입력을 유지한다. 기존 일정·목차·조회 각본은 유지한다.
- 설정된 모델에 실제 연결을 확인하고 임시 DB에서 실제 요청 4건의 추가/삭제·재질문·없는 대상·확인·과거 보존을 검사했다. 대역 자동 검사 61개와 브라우저 9종도 통과했다. 사용자 DB 상태는 서버 재시작 전후 같았다.
- Gemini API 세부·키 분리·오류·검증 기준은 Gemini 계약을 담당 문서로 삼는다. 실제 API 호출 검사는 일반 npm test와 분리한 check:gemini다. 모델 호출 통과는 자유로운 AI 상담·대화 기억·모든 표현 품질이 검증됐다는 뜻이 아니다.

## 루틴 요청의 Gemini 분기 보정 (2026-10-23)

- 사용자 화면에서 “생활 루틴에 명상 항목 제거해줘”가 목데이터 응답으로 끝나는 오류를 확인했다. 기존 각본은 목차까지 항목 이름으로 검색해 실패했고, 서버가 성공한 루틴 제안만 Gemini로 보내는 방식이 원인이었다.
- 성공 여부가 아니라 요청 종류로 분기한다. 기존 해석기의 루틴 추가·삭제 반환값에 요청 표시를 붙여 이름/목차 검색 실패·검증 안내도 Gemini로 보낸다. 기존 일정·목차·조회 범위와 확인 후 저장 규칙은 유지한다.
- 정확한 사용자 문장의 실제 Gemini 추가 중복 안내·삭제 제안을 임시 DB에서 확인했다. 제품 규칙 변경이나 사용자 기록 삭제가 아니다.

## 과정 공유 저장소 반영 (2026-10-23)

- 사용자가 현재 구현을 `201ssc/ax-track-a-2026`에 올려 공유하도록 요청했다. 이번 대상 저장소의 커밋·푸시는 명시적으로 승인된 범위이며, 초기 문서의 ‘커밋·푸시·외부 배포하지 않음’은 이번 요청 이전 작업의 경계다. 앱의 외부 호스팅을 요청하거나 구현한 것은 아니다.
